A cleartext contract has its source in the host package, `host-contracts-cleartext/<vN>`. This package
holds only a generated copy of it, in `pkg/src/_host/` ([FR-20](FR-20.md)). A change reaches this package
only when both packages generate again, in this order:

1. In the host package, run `npm run generate`. It rebuilds the files generated from the contracts,
   including the bytecode that the test stack deploys.
2. In the host package, run `forge test`. It tests the change in the package where you made it.
3. In this package, run `npm run generate`. It copies the new payload of the host package into
   `pkg/src/_host/`.

For example, you fix a bug in `CleartextFHEVMExecutor.sol`:

```bash
cd host-contracts-cleartext/<vN>
# You edit pkg/src/cleartext/CleartextFHEVMExecutor.sol.
npm run generate   # 1. Rebuilds the generated files and the bytecode.
forge test         # 2. Tests the fix in the host package.
cd ../../foundry/forge-fhevm-std
npm run generate   # 3. Copies the fix into pkg/src/_host/.
```

If you skip step 3, the tests of this package still run the old copy, without your fix, and pass.

If the contract is `CleartextFHEVMExecutor`, also check
`ContractSizeLimits.t.sol` — it must stay under EIP-170, while the `…Forge` variant is exempt and
deliberately over. `FhevmVm` is exempt too: it is ETCHED (`vm.etch` skips the creation-time check) and may
grow past 24 KB by design; write no size test against it.

## Before you push

Run these checks, first in the host package, which is the source, then in this package, which consumes it:

```bash
# The host package, the source.
cd host-contracts-cleartext/<vN>
npm run generate && npm run forge:fmt && npm run forge:lint && forge test
MAINNET_RPC_URL=… forge test --match-contract Fork

# This package, the consumer. From the workspace root, the same runs through make:
#   make compile-forge-std lint-forge-std test-forge-std     # or everything: make ci-fast
cd ../../foundry/forge-fhevm-std
npm run generate && npm run lint && forge test
npm run test:consumer                    # the installed @fhevm/forge, by name (FR-04)
SEPOLIA_RPC_URL=… MAINNET_RPC_URL=… npm run test:fork
ARBITRUM_RPC_URL=… MAINNET_RPC_URL=… npm run test:fork        # adds the cleartext-on-a-foreign-chain suite (FR-21)
ARBITRUM_RPC_URL=… MAINNET_RPC_URL=… npm run test:fork-debug  # the same under the fhevm-debug profile (FR-22)
SEPOLIA_RPC_URL=… npm run test:fork-url  # the born-on-a-fork suite, under `forge test --fork-url`
npm run test:anvil                       # starts a throwaway anvil on 8546, runs test/anvil, stops it
```

Use the npm scripts of the host package, not bare `forge fmt` or `forge lint`. The host package keeps the payload under a second profile (`src = pkg/forge/src`), so a bare command formats and lints only `pkg/src`, and reports a clean payload it never looked at. `forge:fmt` and `forge:lint` run all three profiles. The gap does not show in the host package. It shows here, on the generated copy.

If a test says "No tests found in project!" right after you restore or rename a file, the cause is the incremental cache of forge, not the test. Run `forge build --force`, then run the test again.

Both packages end with zero lint notes, zero unused imports, and a clean `forge fmt --check`.

For a stack-too-deep check, loop on `forge build --skip test`, which takes about 0.7 seconds. `forge test` alone does not see a source change that must pass through `generate` to reach the deployed bytecode. The stack is deployed from bytecode generated beforehand, so an edit that is not regenerated tests nothing.
