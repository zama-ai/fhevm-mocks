## This package is two members of the root workspace

The root `package.json` lists both folders of this package in `workspaces`, and `npm-manifest.json` describes both:

| Folder                        | npm name               | What it is            |
| ----------------------------- | ---------------------- | --------------------- |
| `foundry/forge-fhevm-std`     | `@fhevm/forge-std-dev` | The dev package       |
| `foundry/forge-fhevm-std/pkg` | `@fhevm/forge`         | The published package |

A member has no `node_modules` of its own. The workspace installs each dependency once, in the `node_modules` of the root. So `libs` in `foundry.toml` and the lines of `remappings.txt` point at `../../node_modules`, never at a local copy.

## Run every verb from the root, through `make`

Every verb of this package has a `make` target. Run the target from the root of the repository.

| Target                    | What it runs                                                    |
| ------------------------- | --------------------------------------------------------------- |
| `compile-forge-std`       | The compilation                                                 |
| `lint-forge-std`          | The lint                                                        |
| `test-forge-std`          | The offline tests                                               |
| `test-forge-std-fork`     | The fork tests. This target is opt-in.                          |
| `test-forge-std-fork-url` | The tests under `forge test --fork-url`. This target is opt-in. |
| `test-forge-std-anvil`    | The anvil tests. This target is opt-in.                         |

`compile-forge-std` runs after `compile-cleartext-v-cur`, because the payload of this package is copied from `<vN>`, the current host generation.

## The root targets include this package

- `make generate` and `make clean-generated` run this package after `<vN>`. `make check-generated` runs both, so it proves the whole chain in the diagram of [FR-20](FR-20.md).
- `make check-pre` checks the `package.json`, the scripts, the lockfile, and the lint policy of this package against [the npm rules](../../../fhevm-npm/rules/README.md).

## The consumer test is a Foundry project

The published package has a consumer test in `test-consumer/esm`, as [NR-54](../../../fhevm-npm/rules/entries/NR-54.md) requires. The consumer test is a Foundry project, not a Node script. It uses `@fhevm/forge` as a user does:

- `package.json` installs `@fhevm/forge` by name, with `forge-std`, `@fhevm/solidity`, and `encrypted-types`. `forge-std` is a git dependency, pinned to the tag that this package vendors.
- `remappings.txt` points every prefix into `node_modules`.
- `src/AplusB.sol` is the dApp.
- `test/AplusB.t.sol` inherits `TestFhevm`. It encrypts the inputs, runs the dApp, and decrypts the result.
- `npm test` runs `forge build && forge test`.

The `foundry.toml` of the consumer test does not extend `foundry.base.toml`. It repeats the `[fmt]` policy inline. The consumer test is a standalone project that the test runner copies out of the tree, where no `foundry.base.toml` exists. This is the one exception of [NR-30](../../../fhevm-npm/rules/entries/NR-30.md).

In the copy, `forge lint` and `forge test` work only after `npm install`.
