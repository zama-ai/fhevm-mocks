`fhevm-chains.config.json`, at the workspace root, is the one source of every deployed FHEVM address.
`fhevm-npm sync fhevm-chains` renders it from the protocol registry, and `fhevm-npm check fhevm-chains-origin` holds
it to the registry. Every other deployed address in the workspace is a copy of it, and follows it.

## The copies

A copy follows the config in one of three ways, from the best to the weakest:

- It is generated from the config, and never edited by hand. Two copies are generated today:
  - `common-vendored/src/fhevm-chains.ts`, the TypeScript constants: written by
    `fhevm-npm generate chain-constants`, and copied into the Hardhat plugins by `fhevm-npm sync vendored`.
  - `foundry/forge-fhevm-std/pkg/src/StdFhevmChains.sol`, the Solidity table: written by
    `npm run generate:std-fhevm-chains` from `internal/StdFhevmChains.sol.template`.
- It reads the config when it runs, as a forge test can with `vm.readFile`.
- A check compares it with the config.

The evidence of this rule lists the hand-written copies that do none of the three yet.

## The Solidity table

The table is published, and Solidity cannot read JSON, so the table carries the addresses. The generator writes one
entry for each host chain of the `mainnet`, `testnet`, and `devnet` groups. The `local` group is not generated: it is
written in the template. An entry carries:

- the five host contracts of its host
- `kmsGeneration`, or `address(0)` when the host has none
- the gateway's `decryption` and `inputVerification`
- the group's relayer URL
- the chain's alias and default RPC URL, taken from forge-std (see the next section)

`fhevm-npm check forge-std-chains` compares the table with the config, field by field and in both directions, so a
hand-edited table fails.

## Chains that forge-std knows

forge-std knows a chain when its `StdChains.sol` registers the chain's ID. It registers every chain in
`initializeStdChains()`, with one call per chain that gives the alias, the name, the chain ID, and the default RPC URL:

```solidity
setChainWithDefaultRpcUrl("sepolia", ChainData("Sepolia", 11155111, "https://sepolia.infura.io/v3/…"));
```

The installed file is `foundry/forge-fhevm-std/dependencies/forge-std-<version>/src/StdChains.sol`.

A forge test or script reads a chain with `getChain`, by alias or by chain ID:

```solidity
Chain memory sepolia = getChain("sepolia"); // or getChain(11155111)
vm.createSelectFork(sepolia.rpcUrl);
```

`getChain` reverts on a chain ID that forge-std does not know.

The alias and the default RPC URL of a table entry are not in the config. They are forge-std's:
`internal/chain-aliases/ChainAliases.s.sol` asks `getChain` for each chain ID, and writes the answers to
`internal/fhevm-chain-aliases.json`. It uses forge-std's built-in list only, and never calls `setChain`.

## When generation fails

Generation fails on purpose in two cases:

- forge-std does not know a host chain of the config. `make generate` and `make ci` stay red, and
  `check forge-std-chains` fails too, because the table has no entry for that chain.
- A `<ALIAS>_RPC_URL` variable or an `[rpc_endpoints]` entry would replace forge-std's default RPC URL. That URL is
  often private, and it would be published.

Never add an override or a fallback for an unknown chain: its alias and default RPC URL would then be invented in
this workspace, not taken from forge-std. Bump forge-std to a version that knows the chain instead, in three places:

1. `[dependencies]` in `foundry/forge-fhevm-std/foundry.toml`
2. `foundry/forge-fhevm-std/remappings.txt`
3. the remapping in `foundry/forge-fhevm-std/internal/chain-aliases/foundry.toml`

## After a redeploy

When a network group is redeployed, sync the config from the registry, then regenerate every copy with
`make generate`, in the same change. A copy that moves alone has no source, and the next sync can silently undo it.

```sh
# ✅ The config moves, and every copy follows it.
./fhevm-npm-cli sync fhevm-chains --latest && make generate

# ❌ The config moves alone: every copy still gives the old addresses.
./fhevm-npm-cli sync fhevm-chains --latest
```
