`npm-manifest.json#generations` names, for each [generation family](../../definitions/entries/ND-01.md), its `current` generation, `<vN>`, and its `previous` generation, `<vN-1>`. These are its two [live generations](../../definitions/entries/ND-02.md). Both are always there: `previous` is the stack that the upgrade suite of `current` upgrades from. A family names no third generation: `<vN-2>` is retired once `<vN>` arrives.

The two live generations are two different dev packages, each in its own directory below the directory of the family.

## The workspace runs ahead of the networks

The workspace rotates when the developer starts the next generation, not when a network deploys one. Work on a new generation often starts while the current one is not on testnet yet. The rotation then happens anyway: the new generation becomes `current`, the generation before it becomes `previous`, and the one before that is retired from the workspace, even if a network still runs it. So `current` can be a generation that no network runs yet.

## Examples

```jsonc
// ✅ Two live generations.
"host-contracts-cleartext": {
  "current": "./host-contracts-cleartext/<vN>",
  "previous": "./host-contracts-cleartext/<vN-1>"
}

// ✅ Work on the next generation started while <vN> was not on testnet yet.
// The workspace rotated anyway: the new generation is current, and the
// generation before it is previous, although no network runs either yet.
"host-contracts-cleartext": {
  "current": "./host-contracts-cleartext/<vN+1>",
  "previous": "./host-contracts-cleartext/<vN>"
}

// ❌ No previous generation. The upgrade suite of current has nothing to upgrade from.
"host-contracts-cleartext": { "current": "./host-contracts-cleartext/<vN>" }

// ❌ A third generation. The manifest has no place for it, and the schema refuses any other key.
"host-contracts-cleartext": {
  "current": "./host-contracts-cleartext/<vN>",
  "previous": "./host-contracts-cleartext/<vN-1>",
  "older": "./host-contracts-cleartext/<vN-2>"
}

// ❌ The same directory twice.
"host-contracts-cleartext": {
  "current": "./host-contracts-cleartext/<vN>",
  "previous": "./host-contracts-cleartext/<vN>"
}
```

> **Implemented.** The schema of `npm-manifest.json`, which `fhevm-npm check json-schemas` applies, allows only the keys `current` and `previous` for each family, so a third generation fails. The TypeScript validator also requires both to be different dev packages, each below the directory of the family. Nothing requires `previous` yet on `release/0.14.x`: that is the gap, which issue I-120 closes.
