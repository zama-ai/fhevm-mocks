A generation is `major.minor` at every version, so a rendered range is a tilde on the target's central version. A
payload built against contracts `<N>.4` renders `~<N>.4`: at least the version it was built and tested against, up to
the next generation, which the tilde excludes. A tilde stops at the end of the generation both below 1.0
(`~0.14.4` stops before `0.15.0`) and from 1.0 on (`~1.0.4` stops before `1.1.0`). A caret does not: below 1.0 it
accepts the same versions as the tilde, but from 1.0 on `^1.0.4` accepts `1.1.0`, the next generation.

The floor is never lower than the version the payload was built against: a lower one lets a consumer who upgrades the
payload keep, from their lockfile, an older dependency that may lack a fix the payload relies on. A contracts patch
still never forces a payload release; the payload raises its floor on its next release. A prerelease central version
renders exactly, since a tilde range does not match prereleases. This is the one range policy; there is no per-edge
configuration.

The floor makes the publish order binding: `publish check --check-npmjs` requires a published version that satisfies
the range, so the target's version must be on npmjs.com before the payload that renders it.

```jsonc
// ✅ In the v3 plugin's tarball, rendered from the file: link by `publish pack` (target central <N>.4).
"@fhevm/host-contracts-cleartext": "~<N>.4"

// ❌ A caret: from 1.0 on, ^<N>.4 accepts the next generation.
"@fhevm/host-contracts-cleartext": "^<N>.4"

// ❌ The generation floor: a consumer upgrading the plugin can keep contracts <N>.0-<N>.3 and miss a fix.
"@fhevm/host-contracts-cleartext": "~<N>.0"

// ❌ Exact: every contracts patch would force a plugin release, or leave consumers with two copies.
"@fhevm/host-contracts-cleartext": "<N>.4"
```

> **Changed.** Until issue I-123, the renderer wrote a caret below 1.0 and a tilde from 1.0 on. Below 1.0 both accept the same versions, so no published range changes its meaning.
